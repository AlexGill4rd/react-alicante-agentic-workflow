# Skill: Open Release PR

## When to use
- After the changelog has been committed on the release branch and the release is ready for QA.

## Inputs
- `$ARGUMENTS` (required): semver version string. If omitted, read from `package.json`.

## Prerequisites
- **On release branch:** Run `git branch --show-current`. Must start with `release-`. If not → stop and warn.
- **gh authenticated:** Run `gh auth status`. If not → stop, print `gh auth login`.

## Workflow
1. **Create release label:**
   ```bash
   gh label create "release-v<version>" --color "0e8a16" --description "Belongs to release v<version>" 2>/dev/null || true
   ```

2. **Push release branch:**
   ```bash
   git push -u origin release-<x-x-x>
   ```

3. **Read changelog entry** for this version from `CHANGELOG.md` to use as PR body.

4. **Create GitHub QA milestone** (before opening PR so the URL can be included in the body):
   ```bash
   gh api repos/{owner}/{repo}/milestones \
     --method POST \
     --field title="v<version> QA" \
     --field description="QA bugs found during release v<version> testing"
   ```
   Capture the milestone URL from the response (`html_url`).

5. **Open PR targeting `main`:**
   ```bash
   gh pr create \
     --base main \
     --head release-<x-x-x> \
     --title "Release v<version>" \
     --label "release-v<version>" \
     --body "$(cat <<'EOF'
   ## Release v<version>

   ### Summary
   <changelog entries for this version>

   ## QA Milestone
   <milestone URL>

   ## Deploy Checklist
   - [ ] QA passed on Vercel preview
   - [ ] All QA milestone issues closed
   - [ ] New env variables added to Vercel (QA + Production)
   - [ ] DB migrations applied to production (see the Database section of README.md)
   - [ ] Paid product release gate completed if this release touches checkout, subscriptions, billing, Stripe, or paid access
   - [ ] No merge conflicts with main

   🤖 Generated with Claude Code
   EOF
   )"
   ```

6. **Return to user:**
   - PR URL
   - Vercel preview URL (auto-generated by Vercel on PR open) — this is the QA URL. It is specific to the release branch PR, not to be confused with feature branch previews.
   - Milestone URL

## Constraints
- Always target `main` as the base branch — never `dev`.
- Do NOT merge the PR — leave open for QA; user merges when ready.
- Do NOT tag the release — that happens post-merge.

## Output
- PR URL (release → main)
- QA milestone created and linked in the PR body

## Verification
- [ ] `gh pr view` shows base branch as `main`
- [ ] QA milestone exists: `gh api repos/{owner}/{repo}/milestones`
- [ ] PR URL returned to user
